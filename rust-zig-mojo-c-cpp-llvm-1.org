* Teil I: Unterstützte Computerarchitekturen und Betriebssysteme

** Grundsätzliches

Nicht allein die Programmiersprache entscheidet, auf welchen Systemen ein Programm funktioniert.

Entscheidend ist die Kombination aus:

- Programmiersprache
- Compiler
- Standardbibliothek
- Linker
- Zielarchitektur
- Betriebssystem
- ABI
- Betriebssystem-SDK
- C-Laufzeitbibliothek
- unterstützter Toolchain

Eine Sprache kann eine CPU-Architektur grundsätzlich unterstützen, ohne dass für jedes Betriebssystem auf dieser Architektur eine vollständige Toolchain existiert.

Beispielsweise bedeutet:

#+begin_example
ARM64 wird unterstützt
#+end_example

nicht automatisch, dass alle folgenden Systeme gleichermaßen unterstützt werden:

- ARM64-Linux
- ARM64-Android
- ARM64-Windows
- ARM64-macOS
- ARM64-FreeBSD
- ARM64 ohne Betriebssystem

Eine vollständige Zielplattform wird häufig mit einem sogenannten *Target Triple* beschrieben.

Beispiele:

#+begin_example
x86_64-unknown-linux-gnu
aarch64-unknown-linux-gnu
x86_64-pc-windows-msvc
aarch64-apple-darwin
riscv64-unknown-linux-gnu
wasm32-wasi
#+end_example

** Überblick

Die Plattformabdeckung lässt sich grob folgendermaßen einordnen:

| Sprache | Plattformbreite | Cross-Compilation | Embedded | Mobile Systeme |
|---------+------------------+-------------------+----------+----------------|
| C       | hervorragend     | sehr gut          | hervorragend | hervorragend |
| C++     | hervorragend     | sehr gut          | sehr gut | hervorragend |
| Rust    | sehr groß        | gut               | sehr gut | sehr gut |
| Zig     | sehr groß        | hervorragend      | sehr gut | teilweise |
| Mojo    | derzeit klein    | eingeschränkt     | kaum     | kaum |

Nach realer Plattformbreite ergibt sich ungefähr:

1. C
2. C++
3. Rust
4. Zig
5. Mojo

Nach eingebauter und einfacher Cross-Compilation:

1. Zig
2. C und C++ mit Clang
3. Rust
4. Mojo

** Rust

Rust unterstützt zahlreiche Architekturen und Betriebssysteme.

Die Rust-Zielplattformen werden in verschiedene Qualitätsstufen eingeteilt.

*** Rust-Supportstufen

Rust unterscheidet insbesondere:

- Tier 1
- Tier 2
- Tier 3

Tier 1 bedeutet ungefähr:

- Compiler wird offiziell bereitgestellt
- Standardbibliothek wird bereitgestellt
- Zielplattform wird regelmäßig getestet
- Fehler verhindern normalerweise einen Rust-Release

Tier 2 bedeutet ungefähr:

- Compiler und Standardbibliothek können bereitgestellt werden
- Tests sind weniger vollständig
- nicht jedes Ziel wird auf echter Hardware getestet

Tier 3 bedeutet ungefähr:

- der Compiler kennt das Ziel
- Unterstützung kann experimentell sein
- offizielle Binärpakete fehlen möglicherweise
- eigene Toolchain-Builds können erforderlich sein

** Zig

Zig besitzt eine sehr breite Zielarchitektur-Unterstützung.

Eine besondere Stärke von Zig ist die eingebaute Cross-Compilation.

Alle bekannten Ziele können angezeigt werden mit:

#+begin_src sh
zig targets
#+end_src

*** Zig-Zielbeschreibung

Zig verwendet Ziele, die aus mehreren Teilen bestehen:

- CPU-Architektur
- Betriebssystem
- ABI
- CPU-Modell
- CPU-Eigenschaften
- Betriebssystemversion
- libc-Version

Beispiel:

#+begin_src sh
zig build-exe \
  -target aarch64-linux-gnu \
  programm.zig
#+end_src

*** Zig als C- und C++-Compiler

C kompilieren:

#+begin_src sh
zig cc programm.c -o programm
#+end_src

C++ kompilieren:

#+begin_src sh
zig c++ programm.cpp -o programm
#+end_src

C für ARM64-Linux cross-compilieren:

#+begin_src sh
zig cc \
  -target aarch64-linux-gnu \
  programm.c \
  -o programm-arm64
#+end_src

C für Windows cross-compilieren:

#+begin_src sh
zig cc \
  -target x86_64-windows-gnu \
  programm.c \
  -o programm.exe
#+end_src

*** Zig-Zusammenfassung

Zig eignet sich besonders gut für:

- Cross-Compilation
- Betriebssystementwicklung
- Embedded-Systeme
- C-Ersatz
- kleine native Programme
- Compiler und Toolchains
- Build-Systeme
- Programme ohne Garbage Collector
- Software mit expliziter Speicherverwaltung

Die Zahl der theoretisch bekannten Ziele ist sehr groß. Die tatsächliche Reife unterscheidet sich deutlich zwischen den Zielplattformen.

** Mojo

Mojo besitzt derzeit eine wesentlich kleinere Plattformabdeckung als Rust, Zig, C und C++.

Mojo ist stark auf moderne CPUs, MLIR, LLVM, KI-Berechnungen und Hochleistungsrechnen ausgerichtet.

*** Offiziell unterstützte Hostsysteme

Mojo unterstützt hauptsächlich:

| Architektur | Betriebssystem |
|-------------+----------------|
| x86-64      | Linux |
| ARM64       | Linux |
| ARM64       | macOS |

*** Mojo auf x86-64-Linux

Für x86-64 wird eine moderne CPU vorausgesetzt.

Die Anforderungen entsprechen ungefähr der Mikroarchitekturstufe =x86-64-v3=.

Dazu gehören typischerweise CPU-Funktionen wie:

- AVX
- AVX2
- BMI1
- BMI2
- FMA
- weitere moderne x86-Erweiterungen

Geeignete Prozessoren sind ungefähr:

- Intel Haswell oder neuer
- vergleichbare moderne AMD-Prozessoren

Sehr alte x86-64-Prozessoren funktionieren daher nicht.

*** Mojo auf ARM64-Linux und macOS

Mojo unterstützt moderne ARM64-Linux-Systeme.

Als CPU-Klasse wird ungefähr ARM Neoverse N1 oder neuer vorausgesetzt.

Mojo unterstützt macOS auf Apple Silicon:

- Apple M1
- Apple M2
- Apple M3
- Apple M4
- spätere Apple-Silicon-Generationen

Intel-Macs werden nicht offiziell unterstützt.

*** Mojo auf Windows

Mojo wird nicht als normales natives Windows-Programm unterstützt.

Vorgesehene Umgebung:

#+begin_example
Windows
   ↓
WSL
   ↓
Linux
   ↓
Mojo
#+end_example

Die erzeugten Programme sind dabei zunächst Linux-Programme.

*** Mojo auf Android, BSD und RISC-V

Nicht offiziell unterstützt werden insbesondere:

- Android
- Termux
- FreeBSD
- OpenBSD
- NetBSD
- DragonFly BSD
- RISC-V als normale native Mojo-Plattform
- klassische Mikrocontroller
- Bare Metal

Android verwendet Bionic statt glibc und besitzt eine andere ABI und Laufzeitumgebung.

*** Mojo-Cross-Compilation

Mojo kann Zielparameter wie Target Triple und Ziel-CPU verwenden.

Beispiel:

#+begin_src sh
mojo build \
  --target-triple aarch64-unknown-linux-gnu \
  --target-cpu cortex-a72 \
  --emit object \
  -o programm.o \
  programm.mojo
#+end_src

Mojo kann für fremde Ziele unter anderem erzeugen:

- LLVM-IR
- LLVM-Bitcode
- Assemblersprache
- Objektdateien

Für fertige Executables können zusätzlich erforderlich sein:

- externer Linker
- Ziel-Sysroot
- C-Laufzeit
- Zielbibliotheken
- passende Mojo-Runtime
- kompatible Standardbibliothek

*** Mojo und GPUs

Mojo unterstützt GPU-Programmierung insbesondere für:

- NVIDIA-GPUs
- AMD-GPUs
- Apple-Silicon-GPUs

Das ist GPU-Gerätecode innerhalb einer unterstützten Hostumgebung und keine allgemeine zusätzliche Betriebssystemunterstützung.

*** Mojo-Zusammenfassung

Mojo eignet sich derzeit vor allem für:

- moderne x86-64-Linux-Systeme
- moderne ARM64-Linux-Systeme
- Apple-Silicon-macOS
- KI-Berechnungen
- numerische Hochleistungsprogramme
- SIMD
- CPU- und GPU-Kernel
- MLIR-basierte Compilertechnik

Mojo ist derzeit weniger geeignet für:

- Android
- Termux
- Windows ohne WSL
- BSD-Systeme
- RISC-V-Systeme
- alte x86-64-Prozessoren
- Mikrocontroller
- Bare Metal
- exotische Betriebssysteme

*** Einschränkungen von C

Die breite Plattformunterstützung bedeutet nicht, dass jedes C-Programm unverändert überall funktioniert.

Probleme können entstehen durch:

- unterschiedliche Integergrößen
- unterschiedliche Zeigergrößen
- Endianness
- unterschiedliche Betriebssystem-APIs
- unterschiedliche Threadmodelle
- unterschiedliche Dateisysteme
- verschiedene ABIs
- nicht verfügbare Bibliotheken
- undefiniertes Verhalten
- Annahmen über Speicherlayout

*** Unterschied zwischen C und C++ bei kleinen Plattformen

C benötigt oft nur:

- Startcode
- wenige Laufzeitfunktionen
- eventuell keine Standardbibliothek

C++ kann zusätzlich benötigen:

- Konstruktorinitialisierung
- C++-Runtime
- Exception-Unterstützung
- RTTI
- Operator =new= und =delete=
- C++-Standardbibliothek
- Threadunterstützung

Daher kann gelten:

#+begin_example
C vollständig verfügbar
C++-Compiler vorhanden
C++-Standardbibliothek nur teilweise verfügbar
#+end_example

* Teil II: Was ist LLVM?

** Grundidee

*LLVM ist eine modulare Compiler-Infrastruktur.*

LLVM ist kein einzelner Compiler und trotz seines historischen Namens normalerweise auch keine virtuelle Maschine.

Vereinfacht besteht eine Compilerkette mit LLVM aus folgenden Schritten:

#+begin_example
Quellcode
   ↓
Frontend
   ↓
LLVM-IR
   ↓
Optimierungen
   ↓
Maschinencode für x86-64, ARM64, RISC-V usw.
#+end_example

LLVM stellt wiederverwendbare Komponenten bereit für:

- Zwischendarstellungen
- Programmanalysen
- Optimierungen
- Maschinencodeerzeugung
- Objektdateierzeugung
- Linken
- Debugging
- Just-in-time-Kompilierung

** Die drei Hauptteile einer LLVM-Compilerkette

*** 1. Das Frontend

Das Frontend versteht die jeweilige Programmiersprache.

Beispiele:

- *Clang* für C, C++ und Objective-C
- =rustc= für Rust
- der Mojo-Compiler für Mojo
- der Zig-Compiler für Zig
- Swift-Compiler
- Fortran-Compiler wie Flang

Das Frontend erledigt sprachspezifische Aufgaben wie:

- Quelltext lexikalisch analysieren
- Syntax analysieren
- Typen überprüfen
- Namen und Variablen auflösen
- Sprachregeln überprüfen
- Makros oder Generics verarbeiten
- eine interne Zwischendarstellung erzeugen

LLVM selbst versteht nicht automatisch die ursprüngliche Programmiersprache.

LLVM kennt beispielsweise nicht unmittelbar:

- Rust-Lifetimes
- den Rust-Borrow-Checker
- C++-Templates
- Mojo-Traits
- Zig-=comptime=
- Python-Syntax

*** 2. LLVM-IR

LLVM-IR bedeutet:

#+begin_quote
LLVM Intermediate Representation
#+end_quote

Auf Deutsch:

#+begin_quote
LLVM-Zwischendarstellung
#+end_quote

Ein einfaches Beispiel:

#+begin_src llvm
define i32 @add(i32 %a, i32 %b) {
  %result = add i32 %a, %b
  ret i32 %result
}
#+end_src

Dieser LLVM-IR-Code entspricht ungefähr:

#+begin_src c
int add(int a, int b) {
    return a + b;
}
#+end_src

LLVM-IR ist:

- niedriger als C
- höher als konkreter Maschinencode
- streng typisiert
- weitgehend unabhängig von der Ziel-CPU
- für Analysen geeignet
- für Optimierungen geeignet
- als Text darstellbar
- als binärer LLVM-Bitcode speicherbar
- als interne Datenstruktur im Speicher verwendbar

LLVM-IR arbeitet unter anderem mit:

- Funktionen
- Basic Blocks
- Instruktionen
- Registern
- Sprüngen
- Vergleichen
- Speicherzugriffen
- Funktionsaufrufen
- Zeigern
- Vektoren
- atomaren Operationen

**** SSA-Form

LLVM-IR verwendet hauptsächlich die *Static Single Assignment Form*, abgekürzt *SSA*.

Dabei wird jedem virtuellen Register nur einmal ein Wert zugewiesen.

#+begin_src llvm
%a = add i32 %x, %y
%b = mul i32 %a, 2
#+end_src

SSA erleichtert:

- Konstantenpropagierung
- Dead-Code-Elimination
- Datenflussanalyse
- Erkennung redundanter Berechnungen
- Schleifenoptimierungen

*** 3. Das Backend

Das LLVM-Backend übersetzt LLVM-IR in Code für eine konkrete Zielarchitektur.

Typische Zielarchitekturen:

- x86
- x86-64
- ARM
- ARM64 beziehungsweise AArch64
- RISC-V
- PowerPC
- System Z beziehungsweise s390x
- MIPS
- LoongArch
- WebAssembly
- AMDGPU
- NVIDIA PTX beziehungsweise NVPTX

Das Backend übernimmt unter anderem:

- Auswahl konkreter Maschinenbefehle
- Registerzuweisung
- Instruktions-Scheduling
- Umsetzung von Funktionsaufrufen
- Einhaltung der ABI
- Stack-Layout
- CPU-spezifische Optimierungen
- Erzeugung von Assemblercode
- Erzeugung von Objektdateien

** Warum LLVM so wichtig ist

Ohne eine gemeinsame Compiler-Infrastruktur müsste jede Programmiersprache für jede Zielarchitektur ein eigenes Backend entwickeln.

Mit LLVM kann die Architektur vereinfacht werden:

#+begin_example
C ───────┐
C++ ─────┤
Rust ────┤
Mojo ────┤
Swift ───┤
         ↓
      LLVM-IR
         ↓
  LLVM-Optimierungen
         ↓
x86-64 / ARM64 / RISC-V / WebAssembly / GPU
#+end_example

LLVM übernimmt danach einen großen Teil von:

- Optimierung
- Maschinencodeerzeugung
- Unterstützung verschiedener CPUs
- Objektdateierzeugung
- Debug-Informationen

** Wichtige LLVM-Komponenten und Werkzeuge

*** Clang

=clang= ist das C-, C++- und Objective-C-Frontend des LLVM-Projekts.

#+begin_src sh
clang programm.c -o programm
#+end_src

Für C++:

#+begin_src sh
clang++ programm.cpp -o programm
#+end_src

*** llvm-as

=llvm-as= übersetzt lesbare LLVM-IR in binären LLVM-Bitcode.

#+begin_src sh
llvm-as programm.ll -o programm.bc
#+end_src

*** llvm-dis

=llvm-dis= wandelt LLVM-Bitcode zurück in lesbare LLVM-IR um.

#+begin_src sh
llvm-dis programm.bc -o programm.ll
#+end_src

*** opt

=opt= analysiert und optimiert LLVM-IR.

#+begin_src sh
opt -O2 programm.ll -S -o programm-optimiert.ll
#+end_src

*** llc

=llc= übersetzt LLVM-IR oder LLVM-Bitcode in Assemblercode oder Objektcode.

#+begin_src sh
llc programm.ll -o programm.s
#+end_src

Für eine Objektdatei:

#+begin_src sh
llc -filetype=obj programm.ll -o programm.o
#+end_src

*** lld

=lld= ist der Linker aus dem LLVM-Projekt.

Ein Linker verbindet:

- Objektdateien
- statische Bibliotheken
- dynamische Bibliotheken
- Laufzeitbibliotheken

*** LLDB

=lldb= ist der Debugger des LLVM-Projekts.

#+begin_src sh
lldb ./programm
#+end_src

*** llvm-objdump

=llvm-objdump= zeigt Informationen aus Objektdateien und ausführbaren Dateien.

#+begin_src sh
llvm-objdump -d programm
#+end_src

*** Weitere Werkzeuge

| Werkzeug | Aufgabe |
|----------------------+-------------------------------------------|
| =llvm-nm=            | Symbole einer Objektdatei anzeigen        |
| =llvm-readobj=       | Objektdateiformate untersuchen            |
| =llvm-readelf=       | ELF-Dateien untersuchen                   |
| =llvm-ar=            | statische Bibliotheken erstellen          |
| =llvm-strip=         | Symbole und Debug-Daten entfernen         |
| =llvm-link=          | mehrere LLVM-Bitcode-Dateien verbinden    |
| =llvm-cov=           | Code-Coverage auswerten                   |
| =llvm-profdata=      | Profilinformationen verarbeiten           |
| =llvm-size=          | Größen von Binärdateibereichen anzeigen   |
| =llvm-symbolizer=    | Adressen in Symbolnamen umwandeln         |

** Beispiel einer vollständigen LLVM-Kette

Ausgangsprogramm:

#+begin_src c
#include <stdio.h>

int square(int value) {
    return value * value;
}

int main(void) {
    printf("%d\n", square(7));
    return 0;
}
#+end_src

C nach LLVM-IR übersetzen:

#+begin_src sh
clang -S -emit-llvm test.c -o test.ll
#+end_src

LLVM-IR optimieren:

#+begin_src sh
opt -O3 test.ll -S -o test-opt.ll
#+end_src

LLVM-IR in Assembler übersetzen:

#+begin_src sh
llc test-opt.ll -o test.s
#+end_src

Assembler linken:

#+begin_src sh
clang test.s -o test
#+end_src

Programm starten:

#+begin_src sh
./test
#+end_src

Ausgabe:

#+begin_example
49
#+end_example

** LLVM ist nicht der vollständige Compiler

Bei Rust sieht die Kette vereinfacht so aus:

#+begin_example
Rust-Quellcode
   ↓
Lexer und Parser
   ↓
Rust-interne Darstellungen
   ↓
Namensauflösung
   ↓
Typprüfung
   ↓
Borrow Checker
   ↓
Monomorphisierung
   ↓
LLVM-IR
   ↓
LLVM-Optimierungen
   ↓
Maschinencode
   ↓
Linker
   ↓
ausführbares Programm
#+end_example

LLVM kennt dabei nicht:

- Borrow Checking
- Lifetimes
- Traits
- Cargo
- Rust-Makros
- Rust-Module
- Rust-Sichtbarkeitsregeln

Diese Aufgaben übernimmt =rustc= vor der Übergabe an LLVM.

** LLVM und Optimierungen

*** Konstantenfaltung

Aus:

#+begin_src c
int value = 10 * 20;
#+end_src

kann werden:

#+begin_src c
int value = 200;
#+end_src

*** Dead-Code-Elimination

Nicht erreichbarer oder wirkungsloser Code kann entfernt werden.

*** Inlining

Ein Funktionsaufruf kann durch den Funktionskörper ersetzt werden.

*** Schleifenoptimierungen

LLVM kann Schleifen unter anderem:

- entrollen
- vektorisieren
- vereinfachen
- zusammenfassen
- invarianten Code aus der Schleife verschieben

*** Vektorisierung

Skalare Operationen können durch SIMD-Befehle ersetzt werden.

*** Escape- und Alias-Analysen

LLVM untersucht, welche Zeiger auf dieselben Speicherbereiche zeigen könnten.

** Optimierungsstufen

| Stufe | Bedeutung |
|-------+---------------------------------------------------|
| =-O0= | kaum Optimierung, meist besser zum Debuggen       |
| =-O1= | grundlegende Optimierungen                        |
| =-O2= | starke Optimierung ohne extreme Maßnahmen         |
| =-O3= | aggressive Optimierung                            |
| =-Os= | auf geringe Codegröße optimieren                  |
| =-Oz= | noch stärker auf minimale Codegröße optimieren    |

Beispiel:

#+begin_src sh
clang -O3 programm.c -o programm
#+end_src

** LLVM und MLIR

MLIR bedeutet:

#+begin_quote
Multi-Level Intermediate Representation
#+end_quote

Eine Compilerkette kann beispielsweise so aussehen:

#+begin_example
Mojo-Quellcode
   ↓
hochsprachliche MLIR-Darstellung
   ↓
Tensor-Darstellung
   ↓
Schleifen-Darstellung
   ↓
Parallelitäts-Darstellung
   ↓
GPU-Darstellung
   ↓
niedrigere MLIR-Darstellung
   ↓
LLVM-Dialekt
   ↓
LLVM-IR
   ↓
Maschinencode
#+end_example

Solange der Compiler weiß, dass eine Operation beispielsweise eine Matrixmultiplikation ist, kann er sie gezielt optimieren:

- Aufteilung in Blöcke
- Vektorisierung
- Parallelisierung
- GPU-Ausführung
- Nutzung spezieller Tensor-Einheiten
- Anpassung an Cachegrößen

*** MLIR-Dialekte

Beispiele:

- =arith= für arithmetische Operationen
- =func= für Funktionen
- =scf= für strukturierte Kontrollflüsse
- =affine= für affine Schleifen und Speicherzugriffe
- =gpu= für GPU-Ausführung
- =vector= für Vektoroperationen
- =llvm= für LLVM-nahe Operationen
- =tensor= für Tensoren
- =memref= für Speicherreferenzen
- =linalg= für lineare Algebra

Die schrittweise Umwandlung in niedrigere Darstellungen heißt *Lowering*.

** Ist LLVM eine virtuelle Maschine?

Ursprünglich stand LLVM für:

#+begin_quote
Low Level Virtual Machine
#+end_quote

LLVM ist normalerweise keine virtuelle Maschine wie:

- Java Virtual Machine
- .NET Common Language Runtime
- WebAssembly-Runtime
- QEMU

LLVM dient hauptsächlich dazu, Programme zu analysieren, zu optimieren und in nativen Maschinencode zu übersetzen.

LLVM kann allerdings auch Just-in-time-Kompilierung ermöglichen.

** Ahead-of-time- und Just-in-time-Kompilierung

*** Ahead-of-time-Kompilierung

#+begin_example
Quellcode
   ↓
Compiler
   ↓
fertige Binärdatei
   ↓
späterer Programmstart
#+end_example

*** Just-in-time-Kompilierung

#+begin_example
Programm oder Bytecode
   ↓
laufende JIT-Engine
   ↓
Maschinencode wird bei Bedarf erzeugt
   ↓
direkte Ausführung
#+end_example

LLVM besitzt dafür unter anderem ORC JIT.

JIT-Kompilierung wird beispielsweise verwendet bei:

- dynamischen Programmiersprachen
- Datenbankabfragen
- numerischen Kerneln
- Shadern
- Emulatoren
- Laufzeit-Spezialisierung

** LLVM gegenüber GCC

GCC bedeutet:

#+begin_quote
GNU Compiler Collection
#+end_quote

Vereinfacht:

#+begin_example
GCC:
Sprachfrontend + GCC-interne IR + Optimierer + Backend

LLVM:
Frontend wie Clang + LLVM-IR + LLVM-Optimierer + LLVM-Backend
#+end_example

| Bereich | GCC | LLVM/Clang |
|----------------------+----------------------------------+----------------------------------|
| C-Frontend           | GCC                              | Clang                            |
| C++-Frontend         | G++                              | Clang++                          |
| interne Darstellung | GCC-eigene Darstellungen         | LLVM-IR                          |
| Modularität          | historisch stärker monolithisch  | stark bibliotheksorientiert      |
| Fehlermeldungen      | inzwischen gut                   | oft besonders verständlich      |
| Erweiterbarkeit      | möglich                          | häufig gut über Bibliotheken     |
| Lizenz               | GPL                              | Apache-2.0 mit LLVM-Ausnahmen    |
| Linker               | häufig GNU ld oder gold          | häufig LLD                       |
| Debugger             | GDB                              | LLDB                             |

** LLVM gegenüber einer virtuellen Maschine

| Eigenschaft | LLVM-IR | JVM-Bytecode |
|---------------------------+----------------------------------+---------------------------------|
| Hauptzweck                | Compileroptimierung und Codegen  | portable Laufzeitausführung     |
| Typisches Ausführungsmodell | AOT oder JIT                  | normalerweise VM mit JIT        |
| Abstraktionsebene         | relativ niedrig                  | stärker laufzeitorientiert      |
| Speicherverwaltung       | keine vorgeschriebene GC         | normalerweise Garbage Collector |
| Ziel                     | nativer Maschinencode             | JVM-Laufzeitumgebung             |

** Grenzen von LLVM

LLVM stellt nicht automatisch bereit:

- Parser für eine neue Sprache
- Typsystem einer Sprache
- Borrow Checker
- Paketmanager
- Build-System
- Standardbibliothek
- Garbage Collector
- Sprachserver
- vollständige Betriebssystem-SDKs
- Anwendungsframeworks
- automatische Programmsicherheit

Wer eine eigene Sprache mit LLVM entwickelt, muss typischerweise selbst bauen:

- Lexer
- Parser
- AST
- Namensauflösung
- Typprüfung
- Fehlermeldungen
- Laufzeitbibliothek
- Standardbibliothek
- Sprachwerkzeuge
- Übersetzung nach LLVM-IR oder MLIR

** LLVM als Bibliothek

LLVM ist nicht nur eine Sammlung von Kommandozeilenprogrammen.

Ein eigener Compiler kann LLVM verwenden, um:

- Module anzulegen
- Funktionen zu erzeugen
- Basic Blocks zu erstellen
- Instruktionen einzufügen
- Optimierungspässe auszuführen
- Objektdateien zu erzeugen
- JIT-Code auszuführen

LLVM besitzt hauptsächlich eine C++-API, außerdem eine C-API und Bindings für andere Sprachen.

** LLVM-Versionen und Kompatibilität

Zwischen Versionen können sich ändern:

- C++-APIs
- Optimierungspässe
- Kommandozeilenoptionen
- IR-Details
- Standardverhalten
- unterstützte Zielplattformen

LLVM-Bitcode ist nicht zwingend als langfristig stabiles Austauschformat zwischen beliebigen LLVM-Versionen gedacht.

** Kurzer Vergleich der Begriffe

| Begriff | Bedeutung |
|-------------------+---------------------------------------------------|
| Compiler           | übersetzt Programme                               |
| Frontend           | versteht eine konkrete Programmiersprache         |
| AST                | abstrakter Syntaxbaum                             |
| IR                 | Zwischendarstellung                               |
| LLVM-IR            | relativ niedrige LLVM-Zwischendarstellung         |
| MLIR               | Infrastruktur für mehrere Abstraktionsebenen      |
| Optimierungspass   | analysiert oder verändert die Zwischendarstellung |
| Backend            | erzeugt Code für eine Zielarchitektur             |
| Assembler          | übersetzt Assemblersprache in Maschinencode        |
| Linker             | verbindet Objektdateien und Bibliotheken          |
| JIT                | kompiliert während der Programmausführung         |
| AOT                | kompiliert vor der Programmausführung              |
| ABI                | Regeln für binäre Zusammenarbeit                   |
| Target Triple      | Beschreibung der Zielplattform                    |

** Zusammenfassung

Eine typische LLVM-Kette lautet:

#+begin_example
Quellcode
   ↓
sprachspezifisches Frontend
   ↓
LLVM-IR
   ↓
Analysen und Optimierungen
   ↓
Backend
   ↓
Maschinencode
   ↓
Linker
   ↓
ausführbares Programm
#+end_example

Die wichtigsten Punkte:

1. LLVM ist kein einzelner Compiler.
2. Clang ist das C- und C++-Frontend aus dem LLVM-Projekt.
3. LLVM-IR ist eine gemeinsame, relativ niedrige Zwischendarstellung.
4. LLVM kann Code für viele CPUs und Betriebssystemplattformen erzeugen.
5. Rust verwendet LLVM als wichtigstes Standard-Backend.
6. Zig verwendet LLVM für viele Backends, entwickelt aber zusätzlich eigene Compilerkomponenten.
7. Mojo verwendet MLIR und LLVM besonders intensiv.
8. MLIR erhält höherwertige Strukturen wie Tensoren, Schleifen und GPU-Operationen länger im Compiler.
9. LLVM ist normalerweise keine virtuelle Maschine wie JVM oder .NET CLR.
10. LLVM übernimmt nicht die sprachspezifischen Aufgaben wie Parsing, Typprüfung, Borrow Checking oder Paketverwaltung.

Kurz formuliert:

#+begin_quote
Das Frontend versteht die Programmiersprache.

LLVM optimiert die daraus erzeugte Zwischendarstellung.

Das Backend erzeugt Maschinencode für die gewünschte Architektur.
#+end_quote

Oder noch kürzer:

#+begin_quote
Clang versteht C und C++.

rustc versteht Rust.

Der Mojo-Compiler versteht Mojo.

LLVM hilft ihnen anschließend beim Optimieren und Erzeugen von Maschinencode.
#+end_quote
