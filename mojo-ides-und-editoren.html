1. Kurzantwort

Die derzeit beste und vollständigste Entwicklungsumgebung für Mojo ist:

Visual Studio Code mit der offiziellen Erweiterung modular-mojotools.vscode-mojo

Die offizielle Erweiterung funktioniert außerdem in vielen Editoren, die auf Visual Studio Code beziehungsweise Code-OSS beruhen und VS-Code-Erweiterungen unterstützen. Modular nennt insbesondere Cursor.

Helix besitzt mittlerweile eingebaute Mojo-Unterstützung. Emacs, Doom Emacs und Neovim können Mojo über den Mojo-Language-Server verwenden, benötigen aber mehr manuelle Konfiguration. JupyterLab unterstützt interaktive Mojo-Zellen.

3. Was bedeutet „Mojo beherrschen“?

Es gibt mehrere Stufen der Sprachunterstützung.

3.1. Stufe 1: reine Textbearbeitung

Der Editor erkennt lediglich Dateien mit der Endung .mojo.

Mögliche Funktionen:

  • Einrückung
  • Kommentare
  • Klammerpaare
  • grundlegende Syntaxfarben

Das ist noch keine vollständige IDE-Unterstützung.

3.2. Stufe 2: Syntaxparser

Ein TextMate- oder Tree-sitter-Parser erkennt die syntaktische Struktur.

Zusätzliche Funktionen:

  • genauere Syntaxhervorhebung
  • Code-Faltung
  • strukturelle Navigation
  • teilweise automatische Einrückung

3.3. Stufe 3: Language Server Protocol

Der Editor startet mojo-lsp-server und erhält semantische Informationen.

Mögliche Funktionen:

  • Codevervollständigung
  • Fehlermeldungen während des Tippens
  • Hover-Dokumentation
  • Signaturhilfe
  • Symbolnavigation
  • Quick Fixes
  • Formatierung
  • Finden von Deklarationen

3.4. Stufe 4: vollständige IDE-Integration

Zusätzlich zum LSP werden Mojo-spezifische Befehle und Debugger integriert.

Beispiele:

  • aktuelle Datei starten
  • Breakpoints setzen
  • Variablen betrachten
  • Mojo-SDK automatisch erkennen
  • Umgebungen auswählen
  • Format on Save
  • Mojo-Befehle in der Befehlspalette

Diese Stufe bietet gegenwärtig vor allem die offizielle VS-Code-Erweiterung.

4. Visual Studio Code

4.1. Status

Visual Studio Code besitzt die vollständigste offizielle Mojo-Unterstützung.

Die Erweiterung stammt direkt vom Modular-Team: 

modular-mojotools.vscode-mojo

4.2. Unterstützte Funktionen

Die offizielle Erweiterung bietet unter anderem:

  • Syntaxhervorhebung für .mojo-Dateien
  • Codevervollständigung
  • Signaturhilfe
  • semantische Diagnosen
  • Quick Fixes
  • Hover-Dokumentation
  • Navigation zu Symbolen
  • Outline-Ansicht
  • Formatierung
  • Formatierung beim Speichern
  • Ausführung einer Mojo-Datei
  • LLDB-basierte Debugger-Integration
  • LSP-Unterstützung in Codeblöcken von Docstrings
  • automatische Erkennung installierter Mojo-SDKs
  • Auswahl eines bestimmten Mojo-SDKs pro Projekt

4.3. Installation über die Oberfläche

  1. Visual Studio Code öffnen.
  2. Die Erweiterungsansicht öffnen.
  3. Nach Mojo suchen.
  4. Darauf achten, dass der Herausgeber Modular ist.
  5. Die Erweiterung installieren.

4.4. Installation über die Kommandozeile

code --install-extension modular-mojotools.vscode-mojo

4.5. SDK aus einer virtuellen Python-Umgebung verwenden

Bei einer mit uv erzeugten Umgebung kann der Pfad ausdrücklich eingetragen werden.

Beispiel für .vscode/settings.json: 

{
  "mojo.sdk.path": "/root/mojo/.venv",
  "[mojo]": {
    "editor.defaultFormatter": "modular-mojotools.vscode-mojo",
    "editor.formatOnSave": true
  }
}

Der Wert von mojo.sdk.path soll auf das Wurzelverzeichnis der Umgebung zeigen, nicht direkt auf die ausführbare Datei bin/mojo.

Für eine Benutzerinstallation könnte der Pfad beispielsweise so aussehen: 

{
  "mojo.sdk.path": "/home/alex/mojo/.venv"
}

4.6. SDK automatisch erkennen lassen

Die Erweiterung sucht das SDK unter anderem über:

  • eine explizite Einstellung mojo.sdk.path
  • eine SDK-Struktur innerhalb eines Modular-Monorepositorys
  • die von der Python-Erweiterung gewählte Python-Umgebung
  • Pixi-, Conda- oder Wheel-Umgebungen

Wird das falsche SDK gefunden, kann in der Befehlspalette zunächst Folgendes ausgeführt werden: 

Python: Select Interpreter

Danach wird die Umgebung ausgewählt, in der Mojo installiert ist.

4.7. Urteil

Visual Studio Code ist die erste Wahl, wenn möglichst viel ohne manuelle Konfiguration funktionieren soll.

5. Cursor und andere VS-Code-Ableger

5.1. Cursor

Modular nennt Cursor ausdrücklich als unterstützten Editor für die offizielle Mojo-Erweiterung.

Die Erweiterung kann je nach Cursor-Version über den Erweiterungsdialog oder über Open VSX installiert werden.

Suche nach: 

Mojo
Herausgeber: Modular

Cursor erhält damit im Wesentlichen dieselben Mojo-Funktionen wie VS Code:

  • Syntaxhervorhebung
  • LSP
  • Vervollständigung
  • Diagnosen
  • Hover
  • Formatierung
  • Ausführung
  • möglicherweise Debugger-Integration

5.2. VSCodium und Code-OSS

VSCodium und andere Code-OSS-Versionen verwenden häufig Open VSX statt des Microsoft Marketplace.

Die offizielle Mojo-Erweiterung wird ebenfalls über Open VSX angeboten.

Je nach Distribution kann man:

  1. im Erweiterungsdialog nach Mojo suchen;
  2. die Erweiterung aus Open VSX installieren;
  3. eine .vsix-Datei manuell installieren.

Manuelle VSIX-Installation: 

codium --install-extension datei.vsix

5.3. Windsurf und weitere Ableger

Andere VS-Code-kompatible Editoren können die Erweiterung grundsätzlich verwenden, sofern sie:

  • VS-Code-Erweiterungen unterstützen;
  • Zugriff auf den Marketplace oder Open VSX besitzen;
  • die benötigten VS-Code-APIs implementieren;
  • lokale Prozesse wie den Mojo-LSP starten dürfen.

Nicht jeder Ableger garantiert vollständige Debugger- oder SDK-Erkennung. Syntax, LSP und Formatierung funktionieren meist eher als komplexere Debugger-Funktionen.

6. Helix

6.1. Status

Helix besitzt Mojo als eingebaute Sprache. In den offiziellen Helix-Änderungsprotokollen wird Mojo als hinzugefügte Sprache geführt. Später wurden auch Language-Server- und Formatter-Konfigurationen aktualisiert.

Helix bietet damit ohne ein großes Plugin-System:

  • Erkennung von .mojo-Dateien
  • Tree-sitter-Syntaxhervorhebung
  • LSP-Anbindung
  • Formatierung
  • strukturelle Navigation
  • Terminal-basierte Bedienung

6.2. Installation prüfen

hx --health mojo

Die Ausgabe zeigt, ob folgende Bestandteile gefunden werden:

  • Mojo-Language-Server
  • Formatter
  • Tree-sitter-Grammatik
  • Debug-Adapter, sofern vorhanden

6.3. Mojo-Werkzeuge prüfen

command -v mojo
command -v mojo-lsp-server
mojo --version

6.4. Vorteil von Helix

Helix benötigt für viele Sprachen keine separate Plugin-Sammlung. Die Sprachkonfiguration gehört zum Editor beziehungsweise dessen Runtime-Dateien.

6.5. Einschränkung

Die Mojo-Integration wird nicht vom Modular-Team gepflegt. Die Debugger-Integration ist nicht so vollständig und komfortabel wie in VS Code.

6.6. Urteil

Helix ist die beste einfache Terminal-Lösung für Mojo, sofern die installierte Helix-Version aktuell ist und den Mojo-LSP findet.

7. Neovim

7.1. Status

Neovim besitzt keinen offiziellen Mojo-Plugin-Stack vom Modular-Team.

Mojo kann trotzdem gut verwendet werden durch:

  • Neovims eingebauten LSP-Client
  • mojo-lsp-server
  • eine Mojo-Tree-sitter-Grammatik
  • manuelle Dateityperkennung
  • einen Terminalbefehl für mojo run
  • optional eine DAP-/LLDB-Konfiguration

7.2. Voraussetzungen prüfen

command -v nvim
command -v mojo
command -v mojo-lsp-server

7.3. Minimale Dateityperkennung

In ~/.config/nvim/init.lua: 

vim.filetype.add({
  extension = {
    mojo = "mojo",
  },
})

7.4. Minimaler LSP-Start für aktuelles Neovim

Für Neovim-Versionen mit vim.lsp.config() und vim.lsp.enable(): 

vim.lsp.config("mojo", {
  cmd = { "mojo-lsp-server" },
  filetypes = { "mojo" },
  root_markers = {
    "pixi.toml",
    "pyproject.toml",
    ".git",
  },
})

vim.lsp.enable("mojo")

Falls mojo-lsp-server nicht im normalen PATH liegt, kann der absolute Pfad verwendet werden: 

vim.lsp.config("mojo", {
  cmd = {
    "/home/alex/mojo/.venv/bin/mojo-lsp-server",
  },
  filetypes = { "mojo" },
  root_markers = {
    "pixi.toml",
    "pyproject.toml",
    ".git",
  },
})

vim.lsp.enable("mojo")

7.5. Mojo-Datei aus Neovim starten

vim.api.nvim_create_autocmd("FileType", {
  pattern = "mojo",
  callback = function()
    vim.keymap.set(
      "n",
      "<leader>mr",
      function()
        vim.cmd("split | terminal mojo run " .. vim.fn.shellescape(vim.fn.expand("%:p")))
      end,
      {
        buffer = true,
        desc = "Mojo-Datei ausführen",
      }
    )
  end,
})

7.6. Syntaxhervorhebung

Es existieren Community-Grammatiken wie tree-sitter-mojo. Deren Kompatibilität mit der aktuellen Mojo-Syntax und der jeweiligen nvim-treesitter-Generation muss geprüft werden.

Als grober Übergang kann eine .mojo-Datei wie Python hervorgehoben werden. Das ist aber semantisch ungenau, weil Mojo eigene Schlüsselwörter, Eigentumsregeln, Typausdrücke und Compile-Time-Konstrukte besitzt.

7.7. Debugging

Debugging kann über LLDB und nvim-dap eingerichtet werden. Dies ist jedoch keine offizielle Mojo-Neovim-Integration und benötigt eine eigene Startkonfiguration.

7.8. Urteil

Neovim ist für Mojo gut geeignet, wenn der Nutzer LSP, Tree-sitter und Debugger selbst konfigurieren möchte. Es ist nicht so sofort einsatzbereit wie VS Code oder Helix.

8. Emacs und Doom Emacs

8.1. Status

Für Emacs gibt es keine offizielle Mojo-Erweiterung von Modular.

Mojo kann dennoch über einen generischen Major Mode und einen LSP-Client verwendet werden.

Mögliche LSP-Clients:

  • Eglot
  • lsp-mode
  • lsp-bridge

lsp-bridge führt Mojo ausdrücklich in seiner Liste unterstützter Language-Server-Konfigurationen.

8.2. Ein einfacher eigener Mojo-Mode

Diese Konfiguration kann in normales Emacs oder in Doom Emacs übernommen werden.

Für Doom Emacs gehört sie typischerweise nach: 

~/.config/doom/config.el

Konfiguration: 

(define-derived-mode mojo-mode python-mode "Mojo"
  "Ein einfacher Major Mode für die Programmiersprache Mojo."
  (setq-local comment-start "#")
  (setq-local comment-end "")
  (setq-local indent-tabs-mode nil)
  (setq-local tab-width 4))

(add-to-list 'auto-mode-alist '("\\.mojo\\'" . mojo-mode))

(with-eval-after-load 'eglot
  (add-to-list
   'eglot-server-programs
   '(mojo-mode . ("mojo-lsp-server"))))

(add-hook 'mojo-mode-hook #'eglot-ensure)

Danach Doom Emacs neu synchronisieren und starten: 

doom sync

8.3. Absoluten LSP-Pfad verwenden

Liegt Mojo in einer uv-Umgebung, kann der vollständige Pfad eingetragen werden: 

(with-eval-after-load 'eglot
  (add-to-list
   'eglot-server-programs
   '(mojo-mode
     . ("/home/alex/mojo/.venv/bin/mojo-lsp-server"))))

8.4. Mojo aus Emacs starten

Eine einfache interaktive Funktion: 

(defun mojo-run-current-file ()
  "Führe die aktuelle Mojo-Datei mit `mojo run` aus."
  (interactive)
  (unless buffer-file-name
    (user-error "Der aktuelle Puffer besitzt keine Datei"))
  (save-buffer)
  (compile
   (format
    "mojo run %s"
    (shell-quote-argument buffer-file-name))))

(define-key mojo-mode-map
            (kbd "C-c C-r")
            #'mojo-run-current-file)

8.5. Grenzen dieses einfachen Modes

Der Mode erbt seine Syntaxgrundlage von python-mode. Dadurch funktionieren:

  • Einrückung
  • Kommentare
  • viele grundlegende Farben
  • Navigation
  • Eglot-LSP-Funktionen

Nicht exakt abgebildet werden möglicherweise:

  • Mojo-spezifische Schlüsselwörter
  • Traits
  • Ownership- und Argumentkonventionen
  • comptime-Konstrukte
  • spezielle Typausdrücke
  • neue Sprachmerkmale

Der Language Server gleicht einen Teil dieser Schwächen durch semantische Diagnosen und Vervollständigung aus.

8.6. Doom-Emacs-Urteil

Doom Emacs kann Mojo brauchbar bearbeiten und über Eglot oder lsp-bridge semantisch verstehen. Es gibt aber gegenwärtig keine offizielle, vollständig integrierte Mojo-Doom-Schicht.

9. JupyterLab und Jupyter Notebook

9.1. Status

Mojo dokumentiert offiziell die Verwendung in JupyterLab und in Jupyter-Notebook-Umgebungen.

Der aktuelle Ansatz verwendet einen Python-Kernel und lädt mojo.notebook. Mojo-Code wird in Zellen mit der Magic-Anweisung %%mojo ausgeführt.

9.2. Lokale Installation mit Pixi

pixi add mojo jupyterlab ipykernel

JupyterLab starten: 

jupyter lab

9.3. Mojo im Notebook aktivieren

In einer Python-Zelle: 

import mojo.notebook

Danach eine Mojo-Zelle: 

%%mojo

def main():
    print("Hallo aus Mojo")

9.4. Geeignete Einsatzbereiche

JupyterLab eignet sich für:

  • Experimente
  • numerische Berechnungen
  • schrittweise Erklärungen
  • GPU-Beispiele
  • Visualisierung zusammen mit Python
  • Lehrmaterial
  • kurze Benchmarks

9.5. Grenzen

JupyterLab ist kein vollständiger Ersatz für eine Projekt-IDE.

Insbesondere sind große Mehrdateienprojekte, Refactorings und klassisches Debugger-Arbeiten in VS Code oder einem LSP-Editor meist angenehmer.

10. JetBrains-IDEs

Zu den JetBrains-IDEs gehören unter anderem:

  • IntelliJ IDEA
  • PyCharm
  • CLion
  • DataSpell
  • RustRover

10.1. Community-Plugin

Im JetBrains Marketplace existierte beziehungsweise existiert ein Community-Plugin namens Mojo.

Es bot hauptsächlich:

  • grundlegende Bearbeitung
  • Syntaxprüfung
  • Syntaxhervorhebung
  • Kommentare
  • Formatierung
  • teilweise LSP-Anbindung in kommerziellen JetBrains-Varianten

10.2. Wichtige Einschränkung

Das zugehörige öffentliche Repository wurde am 18. Mai 2025 archiviert und ist nur noch lesbar.

Damit besteht ein erhebliches Risiko, dass:

  • neue Mojo-Syntax nicht vollständig erkannt wird;
  • das Plugin mit neueren JetBrains-Versionen nicht kompatibel ist;
  • der aktuelle Mojo-LSP nicht sauber integriert wird;
  • Fehler nicht mehr behoben werden.

10.3. Urteil

JetBrains ist für Mojo derzeit nicht die erste Wahl. Das Community-Plugin kann für einfache Bearbeitung ausreichen, ist aber keine gleichwertige Alternative zur offiziellen VS-Code-Erweiterung.

11. Vim

Vim kann Mojo-Dateien grundsätzlich bearbeiten.

Mögliche Einrichtung:

  • .mojo-Dateien einem eigenen Dateityp zuordnen
  • vorläufig Python-Syntax verwenden
  • einen generischen LSP-Client installieren
  • mojo-lsp-server manuell konfigurieren
  • mojo format als externen Formatter verwenden
  • mojo run über einen Vim-Befehl starten

Eine einfache Dateityperkennung in ~/.vim/ftdetect/mojo.vim: 

au BufRead,BufNewFile *.mojo set filetype=mojo

Ein einfacher Syntax-Fallback in ~/.vim/syntax/mojo.vim: 

runtime! syntax/python.vim
let b:current_syntax = "mojo"

Dieser Fallback ist nicht vollständig korrekt. Neovim oder Helix sind für moderne LSP- und Tree-sitter-Funktionen normalerweise einfacher.

12. Sublime Text

Sublime Text besitzt einen generischen LSP-Client und kann prinzipiell einen über Standard-Ein-/Ausgabe arbeitenden Language Server starten.

Dafür wären notwendig:

  • LSP-Paket für Sublime Text
  • manuelle Sprachdefinition für .mojo
  • Startbefehl mojo-lsp-server
  • gegebenenfalls eine TextMate-Syntax
  • eigener Build-Befehl für mojo run

Eine aktuelle offizielle Mojo-Erweiterung von Modular für Sublime Text ist nicht etabliert.

13. Zed

Zed unterstützt über Erweiterungen:

  • Tree-sitter-Sprachen
  • Language Server
  • Debug-Adapter
  • eigene Sprachdefinitionen

Eine Mojo-Erweiterung wäre deshalb technisch möglich.

Gegenwärtig ist jedoch keine etablierte offizielle Mojo-Erweiterung von Modular für Zed dokumentiert. Ohne eigene oder Community-Erweiterung erkennt Zed Mojo daher nicht in derselben Qualität wie VS Code oder Helix.

14. Reine Kommandozeilenentwicklung

Mojo kann unabhängig von jeder IDE verwendet werden.

Wichtige Befehle: 

mojo --version
mojo run programm.mojo
mojo build programm.mojo
mojo format programm.mojo
mojo test

Mit einem beliebigen Editor kann man daher immer mindestens:

  1. .mojo-Dateien bearbeiten;
  2. im Terminal kompilieren;
  3. das Programm starten;
  4. den Formatter ausführen;
  5. Tests ausführen.

Die IDE entscheidet vor allem über Komfort, nicht darüber, ob Mojo grundsätzlich kompiliert werden kann.

16. Gesamturteil

Die Mojo-IDE-Landschaft ist noch deutlich kleiner als bei Python, Rust, C++ oder Java.

Die Rangfolge lautet gegenwärtig ungefähr:

  1. Visual Studio Code
  2. Cursor und andere gut kompatible VS-Code-Ableger
  3. Helix
  4. Neovim
  5. Emacs beziehungsweise Doom Emacs
  6. JupyterLab für interaktive Aufgaben
  7. JetBrains mit veraltetem Community-Plugin
  8. Vim, Sublime Text und Zed mit eigener Einrichtung

Die wichtigste Unterscheidung ist:

VS Code besitzt eine offizielle vollständige Mojo-Integration.
